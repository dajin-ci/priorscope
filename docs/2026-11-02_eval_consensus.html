PriorScope가 하는 일

투고 전 연구자가 “이 논문은 기존 연구와 뭐가 다른가?”에 근거 위치를 대며 답할 수 있게 돕는 사전 점검 도구입니다. 내 논문과 기존 논문 PDF 한 쌍을 넣으면, 먼저 두 논문이 비교할 만한 쌍인지 판단하고, 비교할 수 있으면 내 논문의 핵심 기술 요소(M)마다 기존 논문 요소(P)와 대응을 근거와 함께 보여줍니다.

사용자
논문 초안을 쓴 공학 계열 대학원생. 지도교수 미팅 전, 리뷰어 지적 대응, Related Work 작성 때.
얻는 것
근거 붙은 요소 대응표, 차별점·겹침, 조건이 같은 실험의 수치 비교, 서술 제안, Related Work 초안. 비교가 부적절하면 그 이유와 다음 행동.
제1원칙
허위 신규 주장을 하지 않는다. 근거를 확인하지 못했거나 판정이 흔들리면 “없음”이 아니라 “확인필요”로 둔다.
하지 않는 것
비교 논문 검색, 논문 우수성 평가, 표절·심사 판정.

전체 파이프라인

서비스(웹·CLI)와 평가(eval/evaluate.py)는 3~7단계를 같은 함수 run_from_extracted로 실행합니다. 그래서 평가 점수가 곧 서비스 동작의 점수입니다. 주황 표시는 오늘 바뀐 곳입니다.

모델 호출 (Studio 에이전트, Solar, 임베딩) 코드 (모델 관여 없음) 조기 종료 · 보조 단계 오늘 바뀐 곳

평가 루프

평가는 추출 결과를 고정한 샘플로 3~7단계만 돌립니다. 같은 PDF를 다시 추출하면 요소 개수가 바뀌어(BERT 8개 → 4개) 라벨 번호가 어긋나기 때문입니다.

오늘 한 일

  1. 과제 재정의와 새 브랜치 확인

    멘토링 피드백(“사용자가 최종 레포트로 무엇을 얻는가”)에 맞춰 목적·사용자·얻는 것을 정리했습니다. 팀원 브랜치 feat/suitability-report-routing을 받아 실행 흐름을 확인하고 테스트 71개 통과를 확인했습니다. 적합성 판단은 Studio가 아니라 Solar 직접 호출이고, 임베딩 유사도가 보조 단계로 들어와 있었습니다.

  2. 평가 라벨 체계를 경로 구조에 맞춤

    라벨을 경로 층(route_label.json, 모든 샘플)과 요소 층(labels.json, 비교 경로일 때만) 두 층으로 나눴습니다. 라벨러는 경로를 직접 고르지 않고 문제·범위·방법 세 축의 관계를 고르며, 경로는 서비스와 같은 select_route로 계산합니다. 규칙 자체를 점검하려고 직감 경로도 함께 받습니다. 샘플 의도는 manifest.json에 적고 S3~S5 선정 기준을 정했습니다.

  3. 추출 공백을 찾아 Prior Paper Agent를 고침

    S1을 라벨링하다가 “원문을 알면 연관된 문제인데 시트만 읽으면 달라 보인다”는 문제를 발견했습니다. 원인은 Prior Paper Agent 스키마에 기여점이 없어, 기존 논문의 문제가 그 논문 기준의 한계로만 추출된 것이었습니다. 축마다 relation_from_sheet를 따로 받아 추출 문제와 판단 문제를 나눠 셀 수 있게 하고, Studio에 contributions를 추가(config v7)했습니다. 재추출로 요소 번호가 밀리지 않게 add_fields.py로 새 필드만 끼워 넣었고, 두 샘플 모두 시트 기준 경로가 원문 기준 경로와 일치하게 됐습니다.

  4. evaluate.py와 공통 실행 함수

    service.py의 3~7단계를 run_from_extracted로 떼어내 서비스와 평가가 같은 코드를 쓰게 했습니다. compare(실제 API), score(API 없이 재채점), stability(PDF로 전체를 여러 번) 세 명령을 만들었습니다.

  5. 첫 실행: 두 샘플 모두 판단 보류

    모델은 판단을 냈는데 코드가 인용을 거부했습니다. 추출본에 남은 PDF 줄바꿈 흔적(mask-ing)을 모델이 고쳐 인용했고, 인용 하나만 틀려도 축 전체를 버리는 규칙 때문이었습니다. 하이픈·공백·대소문자를 양쪽에서 똑같이 무시하는 정규화 대조, 양쪽에 확인된 인용이 하나 이상이면 축 유지, 같은 필드 안에서 잘못 센 번호 정정을 넣고, 탈락한 인용과 사유를 기록하게 했습니다. 이후 경로는 계속 100%입니다.

  6. 판정 기준 확정

    요소 오류를 하나씩 보니 대부분 “유사”의 경계가 정의되지 않아 생긴 불일치였습니다. 아래 기준을 확정해 verdict_rules.py 한 곳에 두고, 비교 PDF 안내문과 라벨 시트가 같은 문구를 쓰게 했습니다. Studio 필드는 1000바이트 제한이 있어 요약만 넣고, 제한을 넘으면 테스트가 실패하게 했습니다. 등급 정답도 사람이 따로 적지 않고 요소 라벨에서 계산합니다.

  7. 세 번 돌려 흔들림을 측정

    같은 설정으로 세 번 실행하자 경로는 모두 같았지만 요소 17개 중 6개(35%)의 판정이 바뀌었고, 두 번째 실행에서는 허위 신규 주장이 20%였습니다. 첫 실행의 0%는 운이었던 것입니다.

  8. Compare Agent 3회 동시 실행과 판정 합치기

    흔들림 자체를 “확신 없음” 신호로 쓰기로 했습니다. 같은 PDF로 Compare Agent를 세 번 동시에 돌려 실행별로 검증한 뒤, 아래 규칙으로 합칩니다. 결과 v9에서 허위 신규 주장률 0%, 요소 정확도 88%, 확인필요 6%가 나왔습니다. 테스트는 135개로 늘었습니다.

확정한 판정 기준

기준 질문: 이 요소를 기존 논문과 다른 점이라고 주장하면, 심사자가 “기존 논문에 이미 있다”고 반박할 수 있는가?

판정해당하는 경우오늘 샘플의 예
일치기존 요소를 그대로 쓰거나 같은 기법. 기존 논문의 사전학습 모델·임베딩 공간을 그대로 쓰는 경우 포함OV-AVEL이 ImageBind 임베딩 공간을 사용
유사같은 역할을 유지한 채 방식을 변형·확장·교체정적 마스킹 → 동적 마스킹, WordPiece → BPE
없음기존에 없는 요소. 기존 요소의 제거, 학습 규모·설정값만 바꾼 것, 범용 기법만 같은 것도 포함. 관련 P는 설명에 적음NSP 제거, 학습 기간·배치 확대, Transformer 블록 사용
확인필요기준으로도 판단이 서지 않을 때. 없음으로 단정하지 않음-

판정 합치기 규칙

실행별 최종 판정(검증 후)을 M 요소마다 합칩니다. 어떤 실행에도 없던 판정을 만들지 않으므로 “검증은 강등만 한다”는 원칙을 지킵니다.

과반 판정
세 번 중 두 번 이상 같으면 그 판정을 씁니다.
겹침 우선
과반이 없음인데 한 번이라도 일치·유사가 나왔으면 확인필요로 둡니다. 겹침을 본 실행이 있다는 것 자체가 없음을 확신할 수 없다는 신호입니다.
과반 없음
세 판정이 모두 다르면 확인필요입니다.
대표 실행
요약·주의 지점·서술 제안은 합친 판정과 가장 많이 일치한 실행의 것을 씁니다. 등급과 커버리지는 합친 판정으로 다시 계산합니다.
