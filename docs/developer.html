01 / OVERVIEW

목적과 범위

논문 두 편의 기술 요소를 비교하고, 사용자가 직접 검토할 근거를 제공합니다.

사용자가 얻는 것

핵심 기술 요소의 대응표, 근거 위치, 비교 가능한 실험 수치, 사람이 다시 확인해야 할 항목입니다.

판단의 범위

선택한 기존 논문 한 편과의 비교입니다. 전체 선행연구에 대한 신규성이나 표절 여부를 확정하지 않습니다.

문서를 읽는 기준
구현 확인은 현재 코드에 동작이 있다는 뜻입니다. 평가 통과를 의미하지 않습니다. 제안은 아직 확정·구현되지 않은 방향입니다.
02 / WORKFLOW

실행 워크플로우

입력 점검 후 두 논문을 추출하고 비교 적합성을 판단합니다. 허용 경로만 이후 비교·검증을 실행합니다. 근거: service.py

실행 전 점검

두 PDF의 SHA-256 해시가 같으면 중단합니다. 필수 환경설정을 확인하고 실행별 폴더를 생성합니다.

  1. 내 논문 분석My Paper Agent
    핵심 기술과 실험 결과를 추출합니다.
    My_Paper.pdf → my_paper.json
  2. 기존 논문 분석Prior Paper Agent
    비교 대상 논문을 같은 방식으로 구조화합니다. 해결 문제나 핵심 기술이 부족하면 다음 단계에서 판단 보류 레포트를 제공합니다.
    Prior_Paper.pdf → prior_paper.json
  3. 비교 적합성 판단Solar + Python
    해결 문제·범위·핵심 방법의 관계와 양쪽 추출 근거를 검사하고 5개 경로 중 하나를 선택합니다.
    suitability.json · 부적합/보류는 report.json 저장 후 종료
  4. 비교용 PDF 생성Python
    기술과 실험 결과에 공통 번호를 부여합니다.
    두 논문 JSON → Compare_Input.pdf
  5. 요소별 비교 분석Compare Agent
    기술 대응, 판정, 설명과 근거 위치를 생성합니다.
    Compare_Input.pdf → compare_result.json
  6. 임베딩 유사도 계산보조 지표
    기술 요소 간 의미 유사도를 계산합니다. 실패해도 코드 검증을 진행하고 오류를 기록합니다.
    기술 요소 → similarity.json (성공 시)
  7. 코드 검증과 결과 구성Validator
    대응 형식·번호·근거·수치를 점검하고 커버리지 범위와 확인 필요 항목을 구성합니다.
    분석 결과 → validated_result.json + 최종 report.json
02A / SUITABILITY

비교 적합성과 레포트 분기

분야 이름보다 해결 문제와 구체적인 방법의 연결을 먼저 봅니다. 실험 비교 가능 여부는 별도로 판단합니다.

판단 축관계근거
해결 문제·목적같음 / 관련됨 / 다름 / 확인 불가문제·기여점 추출 항목
연구 범위·대상대응 가능 / 일부 공통 / 다름 / 확인 불가입출력·대상·전제 조건이 드러나는 추출 항목
핵심 방법구체적 연결 / 범용 기반만 공통 / 다름 / 확인 불가핵심 기술 추출 항목
평가 조건실험 쌍별 비교 가능 / 비교 불가기존 코드 검증의 데이터셋·지표·분할·구성·추가 데이터·단위 검사
경로조건최종 레포트
research
연구 내용 비교		문제가 같고 범위가 대응함요소 대응·차별점 후보·보완 후보·조건별 실험 비교·겹침 지표
partial
공통 범위만 비교		문제가 같으나 범위가 다르거나 일부 공통. 또는 관련 문제이며 범위를 판단할 수 있음공통 범위의 관계 검토와 비교 제한. 전체 연구 등급·차별점·약점 목록은 제외
method
방법론 중심 비교		문제는 다르지만 구체적 방법이 연결됨방법 대응과 적용 대상 차이. 전체 등급·차별점·약점·성능 우위는 제외
unsuitable
비교 부적합 안내		문제가 다르고 방법은 다르거나 범용 기반만 공통양쪽 문제·방법의 근거, 비교 한계, 적절한 비교 대상 선택 안내
insufficient
판단 보류		경로 결정에 필요한 정보·근거가 없거나 분석 응답이 실패함부족한 정보와 재분석 안내
독창성 오판 방지
무관한 논문과 겹치지 않는다는 이유로 독창성이 높다고 표시하지 않습니다. 문제가 달라도 구체적인 방법이 연결되면 방법론 비교를 허용합니다. 실험 조건이 다르다는 이유만으로 기술 비교 전체를 차단하지 않습니다.

근거 확인과 오류 처리

Solar는 축별 관계·이유·양쪽 인용을 구조화된 JSON으로 반환합니다. Python이 허용 관계, 필드, 0부터 시작하는 항목 번호와 인용 문자열의 일치를 검사합니다. 문제 판정은 제목만, 방법 판정은 연구 분야만 인용할 수 없습니다. 검증 실패 축은 확인 불가로 바꾸고 경로를 다시 계산합니다. 의미 판단은 모델의 책임이며 인용 문자열 일치가 의미적 타당성을 증명하지는 않습니다.

해결 문제 또는 핵심 기술이 비어 있으면 API를 호출하지 않고 보류합니다. 적합성 API의 오류·응답 잘림·잘못된 JSON도 정상 비교로 대체하지 않습니다. 부적합/보류에서는 비교 PDF·Compare Agent·임베딩·비교 검증 호출을 생략합니다.

화면·저장·실행 기준

  • report.json: 경로별 요약, 표시 정책, 실험 비교 가능 여부, 다음 행동과 한계. 검증 결과를 기준으로 구성합니다.
  • validated_result.json: 부분/방법론 경로에서는 전체 등급을 적용 안 함으로 저장하고 전체 커버리지 상하한을 비웁니다. 방법론 경로의 수치 비교 목록도 비웁니다.
  • 원본 compare_result.json은 진단 자료로 보존합니다. 연구 비교 경로의 AI 서술은 검증 반영 전 초안으로 별도 접어 표시합니다.
  • 적합성 정보가 없는 이전 샘플은 재분석 안내를 표시합니다. 샘플을 열 때 새 API 호출은 하지 않습니다.
  • CLI도 웹과 같은 run_compare_service()를 사용합니다. 결과는 runs/<run_id>/에 저장되며 이전 output/·result/를 덮어쓰지 않습니다.
python app.py
python check_run.py --run-dir runs/<run_id>

적합성 모델의 기본값은 solar-pro4이며 SUITABILITY_MODEL 환경변수로 변경할 수 있습니다. 동일한 Upstage API 키로 별도 Chat 호출을 한 번 추가합니다. Studio Agent 설정을 다시 배포할 필요는 없습니다. Upstage 공식 Chat API의 구조화 출력 계약을 사용합니다.

현재 한계
적합성은 추출본으로 판단하므로 PDF 추출 누락을 발견하지 못할 수 있습니다. 실제 논문 쌍에 대한 분류 정확도와 원문 근거의 충분성은 아직 평가하지 않았습니다. 부분 비교는 요소별 공통 범위를 자동 확정하지 않고 대응표를 검토 자료로 제공합니다.
03 / DECISIONS

개발 기준과 설계 결정

결정마다 배경, 적용 방식, 확인 근거와 남은 검증을 함께 남깁니다.

설계 결정 8개

DEC-001실행마다 결과 저장 공간을 분리한다구현 확인
배경
동시 실행이나 재실행에서 다른 논문의 결과가 섞이면 비교 근거를 신뢰하기 어렵습니다.
적용
runs/<run_id>/에 입력 PDF, 분석 결과와 임베딩 캐시를 함께 저장합니다.
근거
service.py · run_storage.py
남은 검증
배포 환경에서 여러 사용자의 동시 실행과 결과 접근 범위를 확인해야 합니다.
DEC-002필수 단계 실패 시 분석을 중단한다구현 확인
배경
실패를 이전 결과나 임시 값으로 채우면 다른 실행의 결과가 정상 결과처럼 보일 수 있습니다.
적용
필수 단계의 예외를 StepError로 전달합니다. 임베딩 유사도는 보조 지표이므로 오류를 기록하고 검증을 계속합니다.
근거
service.py의 _run_step()과 유사도 단계
남은 검증
각 단계의 API 오류와 비정상 응답에서 화면 안내를 확인해야 합니다.
DEC-003번호 부여 규칙을 한 곳에서 관리한다구현 확인
배경
비교 입력과 검증 코드의 번호가 다르면 근거와 실제 요소의 연결이 어긋납니다.
적용
ids.py의 assign_ids()를 공유합니다. 같은 JSON과 배열 순서에는 같은 번호를 부여합니다.
근거
ids.py · compare_builder.py · validator.py
제약
추출 항목이나 순서가 바뀐 다른 실행까지 같은 의미의 ID를 보장하지는 않습니다.
DEC-004근거가 불충분하면 확인필요로 처리한다구현 확인
배경
형식 오류나 누락이 있는 판정을 그대로 집계하면 결과를 과신하게 됩니다.
적용
행별 검증 문제가 있거나 대응 행이 빠진 M 요소는 확인필요로 처리합니다. 에이전트의 원래 판정과 처리 이유를 함께 보존합니다.
근거
validator.py의 validate()
제약
코드가 형식과 참조를 검사해도 논문의 의미나 근거의 진실성까지 보장하지는 않습니다.
DEC-005불확실성을 커버리지 범위로 표시한다구현 확인
배경
확인필요 요소를 모두 0점이나 1점으로 확정하면 비교 결과가 한쪽으로 치우칩니다.
적용
확인된 점수로 하한을, 확인필요를 최대 1점씩 포함해 상한을 계산합니다. 두 끝점의 등급이 다르면 판정을 보류합니다.
근거
validator.py의 커버리지 계산
남은 검증
일치 1점·유사 0.5점과 등급 경계 30%·70%의 타당성은 평가 데이터로 검토해야 합니다.
DEC-006입력과 캐시에 보관 기간을 적용한다구현 확인
배경
미공개 논문과 분석 결과를 불필요하게 장기간 남기지 않기 위한 조치입니다.
적용
로컬 실행 폴더의 기본 보관 시간은 24시간입니다. 정리 함수가 호출될 때 만료 폴더를 삭제하며 임베딩 캐시도 같은 폴더에 둡니다.
근거
run_storage.py · service.py
제약
정확히 24시간 뒤에 실행되는 예약 삭제는 아닙니다. 외부 API에 업로드된 파일의 보관·삭제 정책은 별도 확인이 필요합니다.
DEC-007비교 적합성에 따라 분석과 레포트를 분기한다구현 확인
배경
주제가 무관해 겹침이 적은 결과를 높은 독창성으로 오해할 수 있습니다.
선택 이유
해결 문제·범위·구체적인 방법의 연결로 경로를 정하고, 실험 비교 조건을 별도로 판단합니다.
적용
두 논문의 추출 후 Solar 구조화 판단을 실행합니다. 인용 참조 검사 후 연구 비교·부분 비교·방법론 비교·부적합·보류로 나눕니다. 부적합/보류는 후속 비교를 호출하지 않습니다.
근거
suitability.py · comparison_report.py · service.py · streamlit_app.py
검증
5개 경로, 인용 위조·잘못된 참조·잘린 응답·API 실패, 후속 호출 생략, 화면 표시 정책과 CLI 공유 경로를 API 대체 테스트로 확인합니다. 실행 결과는 아래 테스트 항목에 기록합니다.
제약
추출본 인용 검사는 PDF 원문 검증이 아닙니다. 실제 분류 정확도는 별도 평가가 필요합니다. 같은 PDF·개정판 식별과 OCR 품질 판별은 후속 과제입니다.
변경일
2026.10.31 · 이전 제안 상태에서 구현으로 변경
DEC-008비교 화면의 본문 폭과 좌우 여백을 조정한다구현 확인
배경
비교 화면의 내용이 좌우 가장자리에 붙어 보여 긴 설명과 표를 읽기 어렵다는 사용자 피드백입니다.
적용
본문을 최대 1440px로 제한하고 가운데 정렬합니다. 좌우 패딩은 1.25rem~4rem 범위에서 화면 폭의 4%로 조정합니다. 640px 이하에서는 좌우 1rem을 적용합니다.
변경 전후

04 / VALIDATION

판정과 검증 규칙

에이전트의 비교 결과를 코드로 점검하고 계산 결과와 불확실성을 함께 제공합니다.

요소별 판정의미집계
일치기존 논문에 같은 기술 요소가 있다고 판정1점
유사관련 아이디어나 변형된 기술 요소가 있다고 판정0.5점
없음선택한 기존 논문에서 대응 요소를 찾지 못했다고 판정0점
확인필요누락·검증 문제·불충분한 근거 등으로 재검토 필요0~1점 범위
하한 = 확인된 점수 합 ÷ 전체 M 요소 수 × 100
상한 = (확인된 점수 합 + 확인필요 개수) ÷ 전체 M 요소 수 × 100

예를 들어 4개 요소가 일치·유사·없음·확인필요이면 커버리지는 37.5~62.5%입니다. 현재 등급 경계는 30%와 70%이며 범위가 등급 경계를 넘으면 판정 보류로 표시합니다.

수치의 의미
커버리지는 추출된 기술 요소의 대응 정도입니다. 표절률, 신규성 확률, 논문 전체의 유사도 비율로 해석하지 않습니다.

검증 결과에서 함께 볼 항목

  • status · issues · not_checked: 검증 상태, 문제와 검사하지 못한 범위
  • mappings · uncertain_items: 요소별 판정, 근거와 재확인 이유
  • numeric_checks: 데이터셋과 지표가 대응하는 실험 수치의 비교
  • classify_agrees: 에이전트 등급과 코드 계산 등급의 일치 여부

등급 수치만으로 결과의 유효성을 판단하지 않고 검증 상태와 경고를 함께 확인해야 합니다.
